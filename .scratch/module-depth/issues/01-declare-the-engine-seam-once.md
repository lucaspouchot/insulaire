# 01 — Declare the engine seam once

Status: done
Strength: strong
Blocked by: —

**Landed** as one change. `crates/engine/seam.json` declares the 54 methods;
`scripts/generate-seam.mjs` renders the four copies and `npm run check:seam`
fails on a stale one. The deviations from the ticket as written are recorded
under `## Decisions`.

## Problem

The Angular↔engine seam's method list is written by hand five times and
documented a sixth. Every entry is three to six lines of forwarding, and the doc
comment is copied verbatim into the next module down.

| Module | Members |
|---|---|
| `crates/engine/src/lib.rs` — `Engine` | 54 |
| `crates/engine/src/json.rs` — `JsonEngine` | 54 |
| `crates/wasm/src/lib.rs` — `InsulaireEngine` | 55 |
| `apps/web/src/engine/engine.types.ts` — `RawInsulaireEngine` | 55 |
| `apps/web/src/app/services/engine.service.ts` — `EngineService` | 53 |
| `docs/wasm-api.md` | 952 lines |

The three counts that disagree are the point: a method half-lands until every
copy is edited, and nothing catches it.

Sample, the same method in two of the five:

```rust
// crates/engine/src/json.rs:392
pub fn load_character(&mut self, json: &str) -> JsonResult {
    let outcome = self.inner.load_character(json).map_err(|error| err(&error))?;
    ok(&outcome)
}

// crates/wasm/src/lib.rs:391
pub fn load_character(&mut self, json: &str) -> Result<String, JsValue> {
    self.inner.load_character(json).map_err(to_js)
}
```

Every module in this list is **shallow**: its interface is as wide as its
implementation. The deletion test passes on each individually — deleting
`JsonEngine` moves the encoding into the WASM crate, where `cargo test` cannot
reach it — so the seam placement is right and stays. What is wrong is that the
list is stated five times instead of once.

## Deepening

State each method once, in `insulaire-engine`, as a declaration carrying the
name, the parameters, the return shape and the doc comment. Generate from it:

- `JsonEngine`'s body (encode, forward, decode);
- the `#[wasm_bindgen]` methods, including the `js_name` camelCase;
- the `RawInsulaireEngine` declarations in `engine.types.ts`;
- the reference table in `docs/wasm-api.md`.

`Engine` keeps its hand-written typed implementation — that is the module with
behaviour in it. `EngineService` keeps its hand-written signal wiring and its
`parse`/`call` error handling, but its per-method bodies come off the same list.

## What this does not change

ADR-0010 holds unchanged: commands in, snapshots out; content loaded then
referred to by id; bulk data packed; the string contract in `insulaire_engine`
rather than in the WASM crate. This ticket is that decision's own consequence
list being acted on — the ADR already records the friction:

> The method list is not in this ADR. It has grown from ten methods to over
> fifty, and a list copied here would be wrong within a week. `docs/wasm-api.md`
> is the reference […] load-bearing documentation rather than a convenience.

## Open questions

- **Rust macro, or a build script reading a declaration file?** A build script,
  for the reason the question already gives: a macro cannot emit the TypeScript
  or the markdown, and those are two of the four copies. The declaration is
  `crates/engine/seam.json` — data, next to the crate it describes — and
  `scripts/seam.mjs` holds the renderers, following the shape
  `adr-references.mjs` / `check-adr-references.mjs` already set.
- **Does `engine.types.ts` get generated by the same step as ticket 03?** Its
  own step. `RawInsulaireEngine` is the *seam* — 54 methods of `string` in and
  `string` out — while ticket 03's subject is `content-types.ts`, the 85 types
  those strings decode to. They meet in `EngineService` and can share a
  generator later; neither needs the other now.

## Decisions

Settled while implementing, and deviating from the ticket as written:

- **`EngineService` is not generated.** The ticket said its per-method bodies
  "come off the same list". They cannot yet: each returns a typed value
  (`LoadOutcome`, `ResolvedTileRender`) and marshals its arguments
  (`JSON.stringify(choice)`, `ProjectionMode`), and those types are ticket 03's
  subject. Generating it would have pulled 03 into 01. Instead it is *guarded*:
  `unwiredMethods` fails the gate when a declared method is never reached from
  the service, which closes the hole the counts exposed (53 / 54 / 55). The
  other direction needs no check — `RawInsulaireEngine` is generated and typed,
  so `tsc` already refuses a call the seam does not declare.
- **The reference's table is generated, its prose is not.** A method with no
  `###` section fails generation, and the table links to the section's real
  anchor rather than a derived one — so `endGame` and `hasGame`, which share a
  heading, both resolve.
- **The doc comment was reconciled, not picked.** 41 of the 54 pairs had drifted.
  The summary comes from the WASM copy, which was consistently the richer of the
  two, and the `# Errors` section from the facade copy, which was consistently
  the more precise. Five methods documented no errors at all; the declaration now
  requires one of every fallible method, so those five were written.
- **The facade's tests moved to `crates/engine/src/json/tests.rs`.** 1,555 lines
  that cannot live in a generated file. As a child module `super` is still the
  facade, so not one test changed.
- **rustfmt runs inside the generator**, so the gate's formatter has nothing to
  say about generated output and `--check` compares stable text.
- **ADR-0010 was amended, not replaced.** The decision is unchanged; the ticket
  is its consequence list being acted on, which is what the amendment says.
