# 01 — Declare the engine seam once

Status: needs-triage
Strength: strong
Blocked by: —

## Problem

The Angular↔engine seam's method list is written by hand five times and
documented a sixth. Every entry is three to six lines of forwarding, and the doc
comment is copied verbatim into the next module down.

| Module | Members |
|---|---|
| `crates/engine/src/lib.rs` — `Engine` | 54 |
| `crates/engine/src/json.rs` — `JsonEngine` | 54 |
| `crates/wasm/src/lib.rs` — `InsulaireEngine` | 55 |
| `apps/web/src/engine/engine.types.ts` — `RawInsulaireEngine` | 55 |
| `apps/web/src/app/services/engine.service.ts` — `EngineService` | 53 |
| `docs/wasm-api.md` | 952 lines |

The three counts that disagree are the point: a method half-lands until every
copy is edited, and nothing catches it.

Sample, the same method in two of the five:

```rust
// crates/engine/src/json.rs:392
pub fn load_character(&mut self, json: &str) -> JsonResult {
    let outcome = self.inner.load_character(json).map_err(|error| err(&error))?;
    ok(&outcome)
}

// crates/wasm/src/lib.rs:391
pub fn load_character(&mut self, json: &str) -> Result<String, JsValue> {
    self.inner.load_character(json).map_err(to_js)
}
```

Every module in this list is **shallow**: its interface is as wide as its
implementation. The deletion test passes on each individually — deleting
`JsonEngine` moves the encoding into the WASM crate, where `cargo test` cannot
reach it — so the seam placement is right and stays. What is wrong is that the
list is stated five times instead of once.

## Deepening

State each method once, in `insulaire-engine`, as a declaration carrying the
name, the parameters, the return shape and the doc comment. Generate from it:

- `JsonEngine`'s body (encode, forward, decode);
- the `#[wasm_bindgen]` methods, including the `js_name` camelCase;
- the `RawInsulaireEngine` declarations in `engine.types.ts`;
- the reference table in `docs/wasm-api.md`.

`Engine` keeps its hand-written typed implementation — that is the module with
behaviour in it. `EngineService` keeps its hand-written signal wiring and its
`parse`/`call` error handling, but its per-method bodies come off the same list.

## What this does not change

ADR-0010 holds unchanged: commands in, snapshots out; content loaded then
referred to by id; bulk data packed; the string contract in `insulaire_engine`
rather than in the WASM crate. This ticket is that decision's own consequence
list being acted on — the ADR already records the friction:

> The method list is not in this ADR. It has grown from ten methods to over
> fifty, and a list copied here would be wrong within a week. `docs/wasm-api.md`
> is the reference […] load-bearing documentation rather than a convenience.

## Open questions

- Rust macro, or a build script reading a declaration file? A macro keeps the
  declaration next to `Engine`; a build script can also emit the TypeScript and
  the markdown, which a macro cannot.
- Does `engine.types.ts` get generated by the same step as ticket 03, or its own?
  Same generator is likely cheaper.

## Done when

- The 54 entries exist in exactly one place.
- `json.rs`, `wasm/src/lib.rs` and `RawInsulaireEngine` are generated output, not
  reviewed source.
- `docs/wasm-api.md`'s per-method table is generated; its prose stays authored.
- Adding a method to the declaration and nothing else compiles end to end.
- `npm run check` passes.
